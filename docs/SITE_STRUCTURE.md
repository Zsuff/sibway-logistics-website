# Структура сайту та репозиторіїв Sibway Logistics

## 1. Призначення документа

Цей файл — навігаційна карта: де що лежить у двох репозиторіях, який реальний
технологічний стек сайту та як улаштовані каталоги. Він **не є** джерелом
бізнес-фактів (адреса, телефон, метрики, географія) — ці дані підтверджуються
лише в `docs/PROJECT_FACTS.md` та `docs/CONTACTS_USAGE.md`. Він також не описує
затверджений текст сторінок — той живе в `content/`.

Документ призначений для власника, PM і Claude Code (у застосунку на Mac) —
основного інструменту розробки цього проєкту. Antigravity й GitHub MCP
**не використовуються** (див. D-003 у `docs/DECISIONS.md`, `docs/CLAUDE.md`).

`technical/MIGRATION_AND_REDIRECTS.md`.

## 3. Технологічний стек сайту

**Сайт — статичний HTML/CSS/JS без фреймворків і без build-кроку.**

- Розмітка: окремі `.html`-файли на мову (`uk/`, `en/`, `pl/`), без шаблонізатора
  й без серверного рендерингу.
- Стилі: один спільний файл `css/style.css`.
- Скрипти: один спільний файл `js/main.js` (ванільний JavaScript, без збірки).
- Зображення: `img/` (`.webp` для фото, `.svg` для брендингу в `img/brand/`).
- **React, Vite, TypeScript, Node.js, npm/yarn, білд-пайплайн — відсутні.**
  У корені репозиторію коду немає `package.json`, `vite.config.*`, `tsconfig.*`
  чи `node_modules`.

Виняткові файли, що присутні в репозиторії коду, але не є частиною стеку сайту:

- `.claude/settings.local.json` — локальні налаштування Claude Code для цього
  застосунку, не бере участі у виконанні чи збірці сайту.
- `.DS_Store` — системний файл macOS Finder; випадково потрапляє в робочу
  копію, підлягає видаленню з git, коли буде окреме підтвердження.

Якщо в майбутньому в репозиторій коду додасться реальний build-інструмент
(наприклад, збирач для оптимізації зображень чи мінімізації CSS), цей розділ
має бути оновлений з явним підтвердженням власника — до того часу такі
інструменти вважаються відсутніми, а не "основним стеком".

- **Основна мова контенту:** українська (мовні версії — `/uk/`, `/en/`, `/pl/`).
- **Дизайн-джерело:** затверджені макети в `design/approved/` цього репозиторію
  (історично створювались через Stitch; конкретні Project/Screen ID зберігаються
  лише всередині відповідних README у `design/approved/<page>/`, якщо існують,
  і не дублюються тут).
- **Брендинг:** `brand/` (логотипи, кольори, шрифти, патерни).
- **Правила роботи:** `docs/RULES.md`.

## 4. Структура сайт-репозиторію (`sibway-website-`)

Приклад дерева (реальний стан, скорочено — `en/` і `pl/` дзеркалять `uk/`):

```
sibway-website-/
├── index.html                  # редирект на мовну версію
├── 404.html                    # кореневий 404
├── favicon.svg
├── og-image.png                # єдиний банер Open Graph (D-009)
├── robots.txt
├── sitemap.xml
├── css/
│   └── style.css               # спільні стилі для всіх мов
├── js/
│   └── main.js                 # спільний JS (меню, форми, анімації)
├── img/
│   ├── hero-truck.webp
│   ├── about-warehouse.webp
│   └── brand/                  # SVG-логотипи та патерни
├── uk/
│   ├── index.html
│   ├── about.html
│   ├── contacts.html
│   ├── privacy.html
│   ├── terms.html
│   ├── 404.html
│   ├── services.html           # хаб послуг
│   ├── services/
│   │   ├── transport.html
│   │   ├── customs.html
│   │   ├── warehouse.html
│   │   └── audit.html
│   ├── blog.html               # хаб блогу (D-012, UA-only)
│   └── blog/
│       ├── yak-pidgotuvaty-zapyt-na-mizhnarodne-perevezennia.html
│       ├── dokumenty-dlia-mizhnarodnoho-perevezennia.html
│       └── shcho-vplyvaie-na-vartist-mizhnarodnoho-perevezennia.html
├── en/                          # той самий набір файлів, що й uk/ (без blog — D-012)
│   └── ...
└── pl/                          # той самий набір файлів, що й uk/ (без blog — D-012)
    └── ...
```

Кожна мовна версія містить однакову кількість сторінок з однаковою структурою
розділів (правило синхронності з `docs/RULES.md`). Наявні 33 HTML-сторінки:
3 мови × 11 сторінок (`index`, `about`, `contacts`, `privacy`, `terms`, `404`,
`services` + 4 підсторінки послуг), плюс 4 UA-only сторінки блогу (`blog.html`
+ 3 статті) — разом **37 HTML-сторінок**.

**Blog MVP — виняток із три-мовної parity за D-012:** лише UA; EN/PL
відповідники не створюються у v1.

## 6. Модель роботи

1. PM або власник формулює задачу з чіткими межами й критеріями готовності.
2. Claude Code читає `docs/CLAUDE.md` і релевантні документи з репозиторію
   вимог (правила, факти, рішення, поточний контент) перед будь-якими змінами.
3. Claude Code показує план: які файли зачепить, які ризики, як перевірить
   результат — і чекає підтвердження власника.
4. Після узгодженого плану виконуються лише погоджені мінімальні зміни в
   окремій гілці (`feature/…`, `fix/…`, `docs/…`, `chore/…`).
5. Зміни перевіряються (diff, посилання, мови, мобільна версія), показуються
   власнику; коміт, push, pull request, merge і публікація виконуються лише
   після окремого явного підтвердження власника на кожному кроці.

## 7. Джерела істини та пріоритети

При суперечності між документами застосовується такий пріоритет (від
найвищого до найнижчого):

| Пріоритет | Документ | Область |
|---|---|---|
| 1 | `docs/CLAUDE.md`, `docs/RULES.md` | Нормативна інструкція для Claude Code, процесні та контентні правила, безпека git |
| 2 | `docs/DECISIONS.md` | Ухвалені рішення, що явно перекривають інші документи |
| 3 | `docs/PROJECT_FACTS.md` | Бізнес-факти: метрики, контакти, географія, послуги |
| 4 | `docs/CONTACTS_USAGE.md` | Канонічне використання телефонів/месенджерів |
| 5 | `content/{ua,en,pl}/*.md` | Затверджений текст сторінок |
| 6 | `docs/SEO_CONTENT_ROADMAP.md` | SEO- та контентне планування |
| 7 | `docs/DEPLOYMENT.md` | Release/deployment-процес після merge |
| 8 | `docs/SITE_STRUCTURE.md` (цей файл) | Структура файлів і репозиторіїв |
| 9 | `docs/archive/*`, інші чернетки | Історичний робочий матеріал, не джерело істини |

Фактичний код сайту (`sibway-website-`) є джерелом істини щодо того, **що
реально опубліковано зараз**, але не скасовує потребу узгоджувати нові зміни
з правилами й фактами вище.

## 8. Правила актуалізації цього документа

- Оновлюється, коли змінюється реальна структура файлів сайту чи
  контент-репозиторію, склад сторінок, або технологічний стек.
- Будь-яка згадка інструменту, фреймворку чи build-кроку тут повинна
  відповідати фактичному стану репозиторію на момент правки — не
  запланованому чи бажаному стану.
- Розділи про бізнес-факти, контакти, метрики сюди не додаються — вони
  належать `docs/PROJECT_FACTS.md` і `docs/CONTACTS_USAGE.md`.
- Оновлення цього файлу — задача типу `docs/…`, підпорядкована тому самому
  циклу узгодження, що й код (розділ 6).
- Кожна суттєва правка супроводжується коротким записом у
  `docs/CHANGELOG.md`.
